# Findings

- 2026-10-08 — On the Mac, `launchctl bootstrap gui/$UID` can transiently return exit 5 immediately after booting out a Router LaunchAgent; retrying registration succeeded. `command -v node` also resolved to an ephemeral fnm multishell executable, so persistent launchd configuration should use `node -p process.execPath` and retry label registration. After removing a temporary manual Router and restarting the LaunchAgent, the daemon listened on port 17676 and its authenticated peer-info endpoint reported protocol 2 with a reachable backend.
- 2026-10-08 — Windows `devspace.cmd` can reference an absent npm bin entrypoint even though the installed `@waishnav/devspace@1.1.0-beta.4` has a working `dist/cli.js`. Both Windows installation/init and scheduled startup must invoke the latter via the bundled Node runtime. The v0.2 worktree now enforces this contract in tests; physical Windows verification is still required.
- 2026-10-08 — Reinstalling the Windows bundle must stop its own scheduled tasks/private `node.exe` processes before replacing the private runtime; otherwise open executables may prevent in-place replacement. Never target arbitrary system-wide Node processes.
- 2026-10-08 — macOS LaunchAgent executes a staged runtime under `~/.local/share/codassol-router`, not the active Git checkout. Updating a v0.2 branch alone does not upgrade the running Mac Router. A runtime deployment and protocol-2 peer-info check are required.
- 2026-10-08 — A Windows Agent registered with the Mac Router may refer to a different Windows machine than the active Windows browser/client. Never infer installation access or device identity from an unrelated Agent registration; verify the actual target before any remote mutation.
- 2026-10-08 — v0.1.4 still deploys only the Windows Agent; `src/server.js` and routing state reside on the Mac. An offline Mac removes the sole MCP entry point. Peer Router installation and client ingress failover are separate problems; the latter cannot be solved by node-side routing alone.
- 2026-10-09 — The in-memory `DeviceRegistry` is a routing/presence map, not an authoritative UI directory. Heartbeats and peer refreshes can reassert the reported label; a separate persistent `DeviceCatalog` is needed for user aliases. Existing v0.2 peer configuration supports Mac-offline independent Routers, but peer lists are manual and legacy Router IDs can still default to `local`. Registry v1 preserves route IDs, adds installation UUID pins and authenticated eventual metadata convergence; it does not silently migrate IDs or implement zero-config discovery/client endpoint failover.
- 2026-10-08 — The v0.1.3 Windows installer used `(Get-Content ... -Raw).Trim()` on an intentionally empty public `router-default.txt`; PowerShell 5.1 can return `$null` for that file. The v0.2 installer normalizes to `[string]` before trimming to avoid the original null-method failure.
- 2026-10-08 — The Windows `CodasSol DevSpace` scheduled task failed with `MODULE_NOT_FOUND` because its npm-generated `devspace.cmd` shim pointed to `bin/devspace.js`, which was absent from this machine's installed `@waishnav/devspace@1.1.0-beta.4` directory. The published npm tarball does contain that bin file, so the exact cause of its disappearance after installation is unconfirmed. The installed `dist/cli.js` still passed `--version` and served `/healthz`; DevSpace's own package `start` script uses that entrypoint. The Windows bundle now invokes `dist/cli.js` with its private Node runtime for install verification, initialization, and startup.
- 2026-10-08 — On a connected RedMagic 11 Pro (nubia, Android 16), the Mac recognized USB and ADB became authorized. However, the phone's package manager returned `Success: created install session [-1]`, causing both streamed and non-streamed `adb install` to fail with `SecurityException: Caller has no access to session -1`. APK transfer with `adb push` succeeds. USB-install permission or on-device installation requires user action; do not interpret ADB authorization as installation authorization.
- 2026-10-08 — After enabling the USB installation permission on the RedMagic, `adb install -r` returned `Success` for CodasSol Mobile Android V0. The app launched in the foreground (`com.codassol.mobile/.MainActivity`), and the UI accessibility hierarchy reported Router `Connected` and backend `Reachable`. The phone's own `curl` returned HTTP 200 with `{"ok":true,"backendReachable":true}` through `adb reverse tcp:17676 tcp:17676`. Removing the reverse tunnel and tapping `Check connection` displayed `Disconnected / Unavailable`, and restoring the tunnel and tapping again returned `Connected / Reachable`. The Gradle `:app:assembleDebug` build completed successfully; debug APK size about 808 KiB.

- 2026-09-30 — The first Windows bundle could enroll successfully while an existing DevSpace configuration still enforced different `allowedRoots`. The first real Mac -> Router -> Windows `open_workspace` test exposed the mismatch because DevSpace correctly failed closed.
- 2026-09-30 — DevSpace permission roots and Router-advertised Agent roots are one logical policy and must stay synchronized.
- 2026-09-30 — Successful enrollment is not sufficient end-to-end proof. Verification should include a remote `open_workspace` and a follow-up operation on the returned workspace.
- 2026-09-30 — The original public packager auto-detected the build Mac's LAN IP and embedded it in `router-default.txt`. It was not a credential, but it violated the repository's deployment-boundary policy. `v0.1.2` makes public bundles address-free by default.
- 2026-09-30 — Release verification should also scan installer text/examples
  for test-machine-looking identifiers; v0.1.3 replaces those with neutral
  placeholders.
- 2026-09-30 — A live end-to-end test routed from the Mac Router into a Windows Desktop workspace and moved a desktop shortcut to the Windows Recycle Bin.
- 2026-09-30 — A later live session exposed a resilience gap: the Windows Agent heartbeat remained online while its local DevSpace backend became unreachable. The Router could still list the device but remote tool calls failed with an Agent-side fetch error. Device presence and execution-backend health must be tracked separately.

- 2026-10-09 — On the Mac, DevSpace responds at `127.0.0.1:7676/healthz`, while the Router responds at `127.0.0.1:17676/_codassol/health` with separate `backendReachable`. Existing DevSpace is an interactive process, and Router is already managed by `com.codassol.router` LaunchAgent. A menu controller must not kill pre-existing DevSpace or Router processes.
- 2026-10-09 — Reused the transparent `sean.PNG` found under Desktop-Air/seanworkspace/media/images. The menu bar now uses a monochrome NSImage template at 18×18 points, with native dark/light appearance adaptation; only the menu-app bundle is rebuilt, no server restart.
- 2026-10-09 — Renamed the macOS application to CodasSol-mac, now with a color Dock/Finder icon generated from the original `sean.PNG` and a larger 21-point monochrome menu template icon. Menu opening requests an immediate health refresh. The old application was moved to Trash reversibly, with existing DevSpace/Router services left running.
- 2026-10-09 — Native NSMenu auto-disables items with nil actions, making otherwise healthy status rows appear grey. Set `menu.autoenablesItems = false`, mark information rows enabled, and render health as green/red attributed status text. This avoids falsely implying offline status.
- 2026-10-09 — The previously generated Sean menu template icon had a maximum alpha of only 161/255, explaining why it appeared grey even when the services were healthy. The v0.2 asset has opaque 255-alpha pixels and keeps the macOS template tint, with online/offline status conveyed by whole-icon alpha. A full-color `.icns` is now bundled at build time rather than requiring a specific Desktop avatar path.
- 2026-10-09 — On macOS the npm-installed `devspace` entry is a symlink to `bin/devspace.js`, which can suffer the same missing entrypoint bug previously seen on Windows. The package's `dist/cli.js` exists and is the canonical `npm start` target, so the menu's new stable helper validates package identity and resolves that file directly. The helper is installed under Application Support instead of the movable `.app` path, and verifies Node.js >=22. An occupied port is checked separately from the health endpoint before starting a new listener.
- 2026-10-09 — The Mac's legacy DevSpace was PID 1933, while the Router remained an independent `com.codassol.router` LaunchAgent. An independently launched migration worker, with a separate 120-second watchdog and a staged legacy rescue job, switched the port 7676 listener to managed PID 6791. The migration reported `success`, both health URLs returned OK, and the rescue job was not loaded. Physical reboot and real GUI stop/start remain untested to avoid another unannounced interruption.
- 2026-10-09 — Sean requested that the supplied `sean_bnw.png` be used ONLY for the macOS menu bar, while the existing blue application icon remains unchanged. The new `SeanTemplate.png` converts the original white background to alpha transparency and preserves fully opaque dark strokes for native template tinting. - 2026-10-10 — The Mac's production Router still returns HTTP 404 for `/_codassol/devices` and its private state has no `adminToken` yet; do not imply Registry v1 is deployed. The native CodasSol-mac v0.3 panel uses a strictly loopback-only Registry client and a legacy fallback reading only Agent display metadata from local Router state, with unknown (not online) statuses. A separate mocked Node HTTP server verified list schema, authenticated rename and error modes. Native SwiftUI panel compiled with the small Command Line Tools toolchain by avoiding the unsupported `@State` macro, and a separate preview GUI process launched without modifying the running service.
- 2026-10-10 — v0.3.1 review: The installed RedMagic Mobile V0 is a USB-forwarded health client, not a registered Agent or Router. The Mac's legacy files contain Agent `SEANSWPC` and Peer `SEANSWPC-V02`; these may refer to the same physical PC but should not be merged without authoritative identity evidence. Legacy panel includes both as Unknown, hides developer deployment status and unavailable rename controls. DevSpace Stop now verifies the launchd managed PID owns the active TCP/7676 listener. Deferred uncommitted companion experiments were cleared from the separate Registry worktree rather than registering an unverified phone.
- 2026-10-10 — Mac live MCP connected successfully using a full absolute path, while tilde paths could fail and a Windows `C:/...` path was interpreted on macOS as `/Users/sean/C:/...`. Root cause: MCP tools lacked explicit device discovery/selector and routing could choose the sole online local machine when no authorized root matched. Repair staged on `fix/device-routing-v0.2`: discover devices through an authenticated router-side MCP tool, add an optional explicit selector, expand resolvable home paths on their owning node and reject non-matching cross-OS paths. This is source-only pending approved live deployment; device presence is not command execution proof.
- 2026-10-10 — Mac production Registry v1 overlay has two additional compatibility adjustments not represented by the earlier `develop` tree: MCP `mcp-method`/`mcp-name` peer forwarding and a narrowly scoped D:/E: legacy recovery route for rootless `SEANSWPC`. Both are preserved in `fix/device-routing-v0.2` with regression tests so deploying this repair does not inadvertently discard them. C:/ unmatched paths still fail closed instead of going to Mac.
- 2026-10-10 — Mac Router-only routing repair from `fix/device-routing-v0.2` commit `864e368` deployed via detached worker and automatic rollback protection. Live Router PID moved from 33315 to 37206; DevSpace PID stayed 12294, health/Registry v1/peer protocol passed, and private backup was preserved. **Important remaining ingress defect:** ngrok's live tunnel management API reports upstream `http://localhost:7676` (DevSpace), not Router port 17676. Actual ChatGPT CodasSol calls can still bypass Router, evidenced by a `C:/...` path becoming `/Users/sean/C:/...` at DevSpace. The same `C:/...` request directed to localhost Router `17676/mcp` correctly returns `NO_DEVICE_MATCH`. A user-approved ngrok upstream correction and connector tool refresh are required before end-to-end completion; do not treat Router service health as end-to-end MCP validation.
- 2026-10-10 — Approved ngrok maintenance completed using a detached rollback worker: same preexisting fixed domain, only upstream changed from `http://localhost:7676` to `http://localhost:17676`; old ngrok process gracefully stopped, replacement started and independently verified. Public Router `/_codassol/health` now HTTP 200. The local Router (PID 37206) and DevSpace (PID 12294) did not restart. Authenticated MCP `tools/list` through the fixed public endpoint returns seven tools, including `codassol_list_devices`; authenticated discovery returns local Mac online with backend reachable and legacy Windows Agent heartbeat online but backend readiness unknown. Unmatched Windows `C:/...` path fails closed with `NO_DEVICE_MATCH`. A read-only command on an existing Windows Agent-bound workspace returned an internal connector error; Windows execution remains unverified. The ngrok process is currently manually launched rather than confirmed to have reboot autostart, which is a separate resilience task.
- 2026-10-10 — Device Registry v1 mistakenly advertised a heartbeat-only Agent as `backendReachable: true` (`src/server.js` fell back to `routing?.online`). The v0.3.1 Mac menu bar UI then painted all `status: online` nodes green as `Connected`. Direct Windows `open_workspace`/`exec_command` failed despite fresh Agent heartbeats. `fix/mac-device-execution-status-v0.2` addresses both layers: the Router's device API preserves `online` as control-plane presence but returns null for unmeasured Agent backend and execution readiness; the Mac v0.3.2 app remains backward-compatible with older Router replies and always marks heartbeat-only Agents amber (`Agent online`), never ready. A remote Router's healthy backend is also insufficient to claim verified execution. Router-side API fix requires a separately guarded Router restart; menu-only installation has no Router dependency.
